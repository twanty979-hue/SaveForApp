## 🗄️ โครงสร้างฐานข้อมูล (Database Schema)

ระบบใช้งานฐานข้อมูล **PostgreSQL** (รองรับโครงสร้าง Supabase Auth) มีตารางหลักดังนี้:

### 1. `profiles` (โปรไฟล์ผู้ใช้)
เก็บข้อมูลผู้ใช้งานหลัก เชื่อมโยงกับระบบยืนยันตัวตน (`auth.users`)
*   `id` (UUID): ไอดีผู้ใช้ (Primary Key)
*   `display_name` (Text): ชื่อแสดงผล
*   `tier` (Text): สถานะการใช้งาน (`free` หรือ `pro`)
*   `created_at` / `updated_at`: วันเวลาที่สร้างและอัปเดตข้อมูล

### 2. `transactions` (ธุรกรรมรายวัน)
เก็บบันทึกประวัติรายรับและรายจ่ายรายวันของผู้ใช้
*   `id` (UUID): ไอดีรายการ (Primary Key)
*   `user_id` (UUID): เชื่อมโยงกับ `profiles.id`
*   `type` (Text): ประเภทธุรกรรม (`income` หรือ `expense`)
*   `amount` (Numeric): จำนวนเงิน
*   `note` (Text): บันทึกเพิ่มเติม
*   `transaction_date` (Timestamp): วันที่และเวลาที่ทำรายการ

### 3. `dreams` (เป้าหมายการออมเงิน)
บันทึกและติดตามเป้าหมายการออมเงิน (เช่น เงินออมสำหรับแต่งงาน, ซื้อรถ, ไปเที่ยว)
*   `id` (UUID): ไอดีเป้าหมาย (Primary Key)
*   `user_id` (UUID): เชื่อมโยงกับ `profiles.id`
*   `title` (Text): หัวข้อเป้าหมาย
*   `target_amount` (Numeric): จำนวนเงินเป้าหมายที่ต้องการ
*   `current_amount` (Numeric): จำนวนเงินที่ออมได้ในปัจจุบัน
*   `monthly_saving_target` (Numeric): เป้าหมายการออมต่อเดือน
*   `target_date` (Date): วันที่คาดว่าจะเก็บเงินได้ครบตามเป้า
*   `icon` (Text): ไอคอนประจำเป้าหมาย
*   `is_starred` (Boolean): ปักหมุดเป้าหมายสำคัญ

### 4. `fixed_expenses` (รายจ่ายประจำ)
สำหรับจัดการรายจ่ายคงที่ที่ต้องจ่ายเป็นประจำทุกเดือน (เช่น ค่าหอพัก, ค่าสมัครบริการรายเดือน)
*   `id` (UUID): ไอดีรายการ (Primary Key)
*   `user_id` (UUID): เชื่อมโยงกับ `auth.users.id`
*   `name` (Text): ชื่อรายการจ่ายประจำ
*   `amount` (Numeric): จำนวนเงินที่ต้องจ่าย
*   `category` (Text): หมวดหมู่ค่าใช้จ่าย (ค่าเริ่มต้น: `'อื่นๆ'`)
*   `due_day` (Integer): วันที่ต้องจ่ายในแต่ละเดือน (เช่น ทุกวันที่ 5)

### 5. `income_sources` (แหล่งรายได้ประจำ)
แหล่งที่มาของรายได้คงที่ประจำทุกเดือน (เช่น เงินเดือน, ค่าเช่า, ปันผล)
*   `id` (UUID): ไอดีรายการ (Primary Key)
*   `user_id` (UUID): เชื่อมโยงกับ `auth.users.id`
*   `name` (Text): ชื่อแหล่งรายได้
*   `amount` (Numeric): จำนวนเงินรายได้
*   `category` (Text): หมวดหมู่รายได้
*   `receive_day` (Integer): วันที่ได้รับเงินในแต่ละเดือน (เช่น ทุกวันที่ 25)

## 🛡️ การออกแบบระบบ SaaS และการรองรับในระยะยาว (SaaS System Design & Scalability)

สถาปัตยกรรมของ **SaveFor** ได้รับการวางแผนเพื่อรองรับโมเดลธุรกิจ **SaaS (Software as a Service)** และขยายตัวในระยะยาว ดังนี้:

1.  **การแยกข้อมูลผู้ใช้งาน (Multi-tenancy & Data Isolation)**:
    *   ระบบออกแบบให้รองรับผู้ใช้งานจำนวนมากแบบแยกส่วน (Logical Isolation) โดยใช้คอลัมน์ `user_id` เชื่อมกับระบบ Auth เพื่อให้มั่นใจว่าผู้ใช้แต่ละคนจะเห็นและจัดการได้เฉพาะข้อมูลทางการเงินของตัวเองเท่านั้น ป้องกันการรั่วไหลของข้อมูลระหว่างบัญชี
2.  **ระบบแบ่งระดับการใช้งาน (Subscription Tier Enforcement)**:
    *   ในตาราง `profiles` มีคอลัมน์ `tier` ที่รองรับค่า `'free'` และ `'pro'` เพื่อควบคุมการจำกัดสิทธิ์การใช้งาน (Usage Limits & Feature Flags)
    *   **Free Tier**: จำกัดจำนวนเป้าหมายการเงิน (Dreams) หรือจำกัดฟังก์ชันการวิเคราะห์รายจ่ายประจำ (Fixed Expenses)
    *   **Pro Tier**: เปิดใช้งานฟีเจอร์พรีเมียมเต็มรูปแบบ ไม่จำกัดเป้าหมายการออม และเข้าถึงรายงานเชิงลึก
3.  **โครงสร้างฐานข้อมูลที่ยืดหยุ่นต่อการเปลี่ยนแปลง (Database Extensibility)**:
    *   **การเพิ่มฟีเจอร์/คอลัมน์ใหม่**: สามารถทำได้ง่ายผ่านระบบ Database Migration เช่น การเพิ่มคอลัมน์เก็บประวัติการชำระเงิน หรือการเชื่อมระบบรับชำระเงิน (Payment Gateway) สำหรับสมัครสมาชิก Pro Tier โดยไม่ส่งผลกระทบต่อข้อมูลการใช้งานเดิม
    *   **การระบุตัวตนด้วย UUID**: ใช้ UUID เป็น Primary Key ในทุกตารางเพื่อความปลอดภัยและประสิทธิภาพการรองรับผู้ใช้พร้อมกันปริมาณมาก (High Concurrency)
4.  **ความปลอดภัยและการกรองข้อมูลผ่าน Middleware (Go API Gateway)**:
    *   ฝั่ง Go Backend จะทำหน้าที่เป็นตัวกรองสิทธิ์ (Authorization Middleware) คอยตรวจสิทธิ์โทเค็นของผู้ใช้ และเช็กระดับสมาชิก (`tier`) ก่อนจะอนุญาตให้เข้าถึงหรือบันทึกข้อมูลใด ๆ เสมอ ช่วยเพิ่มความมั่นคงปลอดภัยให้กับผู้ใช้บริการ

## ⚙️ สิ่งที่กำลังจะพัฒนาเพิ่มเติมและเหตุผล (What & Why)

ในการพัฒนาขั้นต่อไป เราจะเริ่มทำสิ่งเหล่านี้ และมีเหตุผลประกอบดังนี้:

### 1. การเชื่อมต่อฐานข้อมูลและตั้งค่า Migration ในฝั่ง Backend (Go API)
*   **ทำอะไร**: ตั้งค่าโฟลเดอร์สำหรับทำ SQL Migration และเชื่อมต่อฐานข้อมูล PostgreSQL ผ่าน ORM หรือ Database Driver ใน Go
*   **ทำไมต้องทำ**: เพื่อให้สามารถแก้ไขโครงสร้างตาราง (เช่น เพิ่ม/ลดคอลัมน์) ได้อย่างมีระบบและมีประวัติบันทึก (Version Control) เมื่อรันระบบบนสภาพแวดล้อมที่ต่างกัน (Development, Staging, Production) โครงสร้างจะตรงกัน 100%

### 2. การสร้าง RESTful API endpoints สำหรับ CRUD (Create, Read, Update, Delete)
*   **ทำอะไร**: พัฒนา endpoint เช่น `/api/transactions`, `/api/dreams` และ `/api/recurring`
*   **ทำไมต้องทำ**: เพื่อให้ระบบ backend พร้อมทำหน้าที่ตรวจสอบความถูกต้องทางธุรกิจ (Business Logic Validation) ก่อนบันทึกข้อมูล และช่วยให้ทีม Flutter สามารถเรียกใช้ข้อมูลที่เป็นมาตรฐานเดียวกันผ่าน JSON format

### 3. การสร้าง Data Model และ API Service ในฝั่ง Frontend (Flutter App)
*   **ทำอะไร**: แปลง JSON จาก API ของ Go มาเป็นโมเดลภาษา Dart เพื่อนำไปใช้งานต่อในหน้าจอแอป
*   **ทำไมต้องทำ**: เพื่อจำกัดขอบเขตการเขียนโค้ดและอำนวยความสะดวกในการจัดเก็บข้อมูลภายในเครื่อง (Local Caching) ในอนาคต อีกทั้งช่วยให้โค้ดมีความเป็นระเบียบและไม่เกิดข้อผิดพลาดจากประเภทข้อมูลที่ผิดเพี้ยน

## 🚀 แผนการพัฒนาถัดไป (Roadmap & Next Steps)

### ระยะที่ 1: ตั้งค่าฐานข้อมูลและระบบหลังบ้าน (Backend Server Setup)

- [ ] ออกแบบ Data Models และ Database Driver
- [ ] พัฒนา RESTful API endpoints สำหรับแต่ละตาราง:

  - **Dreams**: การอัปเดตยอดออมเงิน / การคำนวณเป้าหมายรายเดือน

### ระยะที่ 2: เชื่อมโยงฝั่งหน้าบ้าน (Frontend App Development)

- [ ] พัฒนาโมเดลข้อมูลฝั่ง Dart ให้ตรงกับฝั่ง Database

### ระยะที่ 3: พัฒนา UI/UX (User Interface Development)
- [ ] **หน้าหลัก (Dashboard)**: แสดงสรุปรายรับ-รายจ่ายของเดือนปัจจุบัน, ยอดเงินคงเหลือ, และความคืบหน้าของเป้าหมาย (Dreams)
- [ ] **หน้ารายการธุรกรรม (Transactions)**: แสดงรายการประวัติ, คัดกรองตามหมวดหมู่ หรือสลับดูรายเดือน
- [ ] **หน้าเป้าหมายการเงิน (Dreams)**: แสดงความก้าวหน้าในรูปแบบกราฟ/เปอร์เซ็นต์ พร้อมปุ่มกดอัปเดตยอดออม
- [ ] **หน้ารายจ่าย/รายรับประจำ (Recurring items)**: แสดงรายการประจำเดือนเพื่อช่วยเตือนความจำ
